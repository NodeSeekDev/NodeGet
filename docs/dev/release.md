# 发布流程

本文面向负责发版的维护者，说明怎么发布 beta、rc 和正式版。用户怎么安装这几档版本，见[安装预发布版和 nightly](../guide/install/install-script.md#安装预发布版和-nightly)。

## 三档发布

| 档位 | 版本号示例 | 谁来触发 | 从哪个分支构建 | 说明 |
|---|---|---|---|---|
| nightly | `nightly` | 自动，每天一次 | `dev` | 滚动更新，不需要人操作 |
| 预发布 | `v0.7.0-beta.1`、`v0.7.0-rc.1` | 维护者手动 | `main` | beta 功能可能还在变化，rc 已冻结功能、只修阻塞问题 |
| 正式版 | `v0.7.0` | 维护者手动 | `main` | 面向所有用户，默认安装的就是这一档 |

三档的区别由版本号决定：版本号**带 `-` 后缀**（`-beta.1`、`-rc.1`）就是预发布，不带就是正式版。

| | 预发布 | 正式版 |
|---|---|---|
| GitHub Release | 标记为 Pre-release，不会成为 Latest | 标记为 Latest |
| Docker 镜像 | 只推送对应版本的标签（如 `v0.7.0-rc.1`） | 推送版本标签，同时更新 `latest` |

所以发预发布不会影响只装正式版的用户：安装脚本和 Docker 的 `latest` 都不会指向它。

## 发布只能手动触发

发布工作流（`release`）只有手动运行这一个入口。**推送 tag 不会触发发布**，也不要手动打 tag：tag 由发布流程在创建 Release 时自动生成，指向运行时所选分支的最新提交。

## 发布一个版本的步骤

预发布和正式版步骤相同，只是版本号不同。

### 1. 确定版本号

版本号写在根目录 `Cargo.toml` 的 `[workspace.package]` 里，发布流程读取它并加上 `v` 前缀作为 tag。

| 要发的版本 | `Cargo.toml` 里的版本号 |
|---|---|
| beta | `0.7.0-beta.1`，下一个 beta 是 `0.7.0-beta.2` |
| rc | `0.7.0-rc.1`，下一个 rc 是 `0.7.0-rc.2` |
| 正式版 | `0.7.0` |

同一个版本通常按 `beta → rc → 正式版` 的顺序走，版本号的大小关系是 `0.7.0-beta.1 < 0.7.0-rc.1 < 0.7.0`。不一定每个版本都要发 beta 或 rc，小的修复版可以直接发正式版。

### 2. 修改版本号并合并到 main

1. 在 `dev` 上提交一次版本号修改，只改 `Cargo.toml` 的版本号，以及随之变化的 `Cargo.lock`（改完执行一次 `cargo check` 即可更新）。提交说明沿用以前的写法，如 `Chore: bump version to 0.7.0`。
2. 把 `dev` 合并到 `main`（走 dev→main 的 PR）。

这个顺序和 0.6.0 的做法一致。

### 3. 先试跑一次（建议）

在 GitHub 的 Actions 页面，选择 `release`，点 **Run workflow**：

- **Use workflow from** 选 `main`。
- **不勾选**发布选项。

这样只做全平台构建，不创建 Release，也不推送镜像。构建全部通过，说明这个提交可以发布。

### 4. 正式发布

同样的位置再运行一次，这次**勾选** "Create/update the GitHub Release and Docker image"。

流程会完成：

1. 全平台构建。
2. 创建 GitHub Release（预发布或正式版，由版本号决定），上传所有平台的文件。
3. 推送 Docker 镜像。

### 5. 发布后检查

在 Release 页面确认：

- 预发布的标记是 Pre-release，正式版带有 Latest 标记。
- 文件齐全，各平台的主控和被控文件都在。
- Docker Hub 上有对应的版本标签。发预发布时，`latest` 的指向没有变化；发正式版时，`latest` 已经指向新版本。

再用安装脚本实际装一遍，确认真的能装、能启动：

```bash
# 预发布
releases_tag=v0.7.0-rc.1 bash <(curl -sL https://install.nodeget.com) install-server
```

## 发错了怎么办

**同一个版本号不要重复发布。**对同一个版本号再运行一次，会覆盖已有 Release 里的同名文件和 Docker 镜像标签，已经下载过的人拿到的内容和现在不一致，很难排查。

发现问题时：

- **预发布阶段**：修复后升一个预发布号重发，如 `rc.1` 之后发 `rc.2`。
- **正式版**：修复后升补丁号，如 `0.7.0` 之后发 `0.7.1`。

## 用户升级时的版本规则

这些规则决定了版本号的写法为什么要这么规范：

- 主控和被控升级时，**只能升级到正式版**，目标版本号必须是纯数字（`v0.7.0`）。
- 当前运行的是 nightly 或预发布（版本号带后缀）时，一定会被判定为"可以升级"，即使数字部分和正式版相同。比如运行 `0.7.0-rc.1` 的节点，可以升级到 `0.7.0`。
- 允许降级。

## nightly

nightly 不需要维护者操作：

- 每天北京时间 02:00 自动从 `dev` 构建，覆盖全部平台。
- 如果 `dev` 自上次 nightly 以来没有新提交，当天会跳过。
- 构建出的版本号是当前版本号加日期后缀，如 `0.7.0-nightly.20261011`。
- 它滚动更新名为 `nightly` 的预发布，并推送 Docker 的 `nightly` 标签，不会影响 `latest`。

需要立刻出一个 nightly 时，在 Actions 页面手动运行 `nightly` 即可。
